1. Visión General

El sistema Academia Chat-Driven es una plataforma educativa que utiliza inteligencia artificial conversacional como única interfaz de usuario. La arquitectura se basa en tres pilares fundamentales:

Componentes Principales

Cliente Móvil (Android)

  • Aplicación Kotlin con Jetpack Compose
  • Única pantalla (ChatScreen) para toda la interacción
  • Sistema de navegación mediante contexto conversacional
  • Soporte para modo Mock (desarrollo) y Real (producción)

Backend Chat (Orquestador)

  • Servidor Spring Boot (Java 21) que actúa como intermediario
  • Gestión de autenticación JWT para usuarios
  • Integración con OpenAI GPT-4 para procesamiento de lenguaje natural
  • Orquestación de llamadas a herramientas (tool calling)
  • Estructuración de respuestas según contrato Envelope
  • Reenvía el JWT del usuario a API Workers (concepto de "token delegado")

API Workers (Python/Flask)

  • API REST con lógica de negocio
  • Autenticación mediante JWT (el mismo del usuario)
  • Acceso directo a base de datos MySQL
  • Endpoints para gestión académica completa
  • Validación de permisos a nivel de negocio
  • Despliegue: AWS Elastic Beanstalk

Base de Datos (MySQL 8.0)

  • Modelo relacional normalizado
  • Sistema de auditoría con timestamps
  • Seguridad mediante prepared statements
  • Conexiones:
    • Desarrollo: mysql://user:pass@localhost:3307/api_workers

Concepto Clave: Token Delegado

¿Qué es el Token Delegado?

El "token delegado" es el mismo JWT del usuario que viaja sin modificación desde Android hasta MySQL, pasando por Backend Chat y API Workers. No es un token diferente, sino una delegación de la identidad del usuario a través de todas las capas del sistema.

Flujo del Token Delegado:

Usuario login → JWT generado (API Workers)
  ↓
Android guarda JWT
  ↓
Backend Chat recibe JWT (valida claims)
  ↓
Backend Chat REENVÍA el MISMO JWT a API Workers
  ↓
API Workers valida el MISMO JWT
  ↓
MySQL registra usuarioId del JWT en auditoría

Ventajas del Token Delegado:

  1. Trazabilidad Completa: Cada acción en cada capa está asociada al mismo usuarioId
  2. Simplicidad: Un único secret compartido entre Backend Chat y API Workers
  3. Multi-tenancy Automático: El academiaId del JWT filtra datos en todas las capas
  4. Sin Conversión de Credenciales: No hay transformación de tokens (menor superficie de ataque)
  5. Logs Correlacionables: Los logs distribuidos se pueden correlacionar por usuarioId

Contraste con API-Key (NO usado):

  • API-Key autentica el servicio (Backend Chat como cliente)
  • JWT autentica al usuario (persona que usa la app)
  • En nuestro sistema, ambos backends están bajo el mismo control → solo necesitamos JWT

Por Qué NO Usamos API-Key

Ventajas de JWT Único:

  1. Simplicidad: Una sola clave en todo el sistema
  2. Trazabilidad: Sabemos qué usuario hizo cada acción en cada capa
  3. Multi-tenancy automático: El JWT lleva academiaId, filtra datos automáticamente
  4. Menos superficie de ataque: No hay que rotar API-Keys
  5. Control total: Ambos backends están bajo nuestro control

Cuándo SÍ usar API-Key:

  • Cuando terceros necesitan acceder a tu API sin usuarios (ej: Moodle, Google Classroom)
  • Cuando el servicio que llama no tiene acceso al JWT del usuario
  • Cuando quieres autenticar el servicio (no el usuario)

En nuestro caso:

  • Backend Chat y API Workers están bajo el mismo control
  • Backend Chat siempre tiene el JWT del usuario
  • Más simple = más seguro

Capas de Seguridad Implementadas

Capa 1: Transporte

  • HTTPS obligatorio en todas las comunicaciones
  • TLS 1.3 para cifrado end-to-end
  • Certificados SSL/TLS válidos

Capa 2: Autenticación de Usuario (JWT en 3 puntos)

  • Android → Backend Chat: JWT con firma HMAC-SHA256
  • Backend Chat → API Workers: EL MISMO JWT reenviado
  • API Workers → MySQL: Extrae claims del JWT para filtrar datos

Claims del JWT:

{
  "usuarioId": 12,
  "academiaId": 5,
  "role": "Profesor_academia",
  "email": "maria@academia.com",
  "iat": 1698073000,
  "exp": 1698073900
}

Capa 3: Autorización a Nivel de Negocio

  • Validación de permisos según rol (Admin_plataforma, Admin_academia, Profesor_academia)
  • Filtrado de datos por academiaId (multi-tenancy)
  • Solo acceso a recursos propios (profesor solo ve sus clases)

Capa 4: Base de Datos

  • Prepared Statements para prevenir SQL Injection
  • Usuario de BD con permisos limitados (no DROP, no ALTER)
  • Conexiones cifradas (SSL/TLS)
  • Auditoría con timestamps (fecha_alta, fecha_ultima_modificacion)

Capa 5: Rate Limiting y Anti-Abuse

  • Límite de 100 requests/minuto por usuario en Backend Chat
  • Límite de 1000 requests/minuto por IP en API Workers
  • Bloqueo temporal tras 5 intentos fallidos de login (locked_until en Usuario)
  • Captcha tras 3 intentos fallidos (futuro)

⭐ Optimización de Performance añadida en v2.1.0:

Se agregó el campo academia_id INT NOT NULL a la tabla Inscripcion con:

  • Propósito: Evitar JOINs al filtrar inscripciones por academia (mejora 50%+ en queries)
  • Índice: idx_inscripcion_academia para búsquedas rápidas
  • Foreign Key: fk_inscripcion_academia → Academia(id)
  • Validación: 2 triggers MySQL garantizan consistencia:
    • trg_inscripcion_academia_check_insert - Valida que alumno y curso pertenecen a la misma academia
    • trg_inscripcion_academia_check_update - Valida cambios en academia_id, alumno_id o curso_id
  • Auto-población: El campo se calcula automáticamente desde alumno.academia_id

Nota de Arquitectura: Esta denormalización controlada prioriza performance sobre normalización estricta, crítica en aplicaciones multi-academia con alto volumen de queries de filtrado.

5. Contrato de Respuesta del Chat

Estructura del Envelope

Todas las respuestas del Backend Chat siguen un contrato estandarizado llamado Envelope, que permite renderizar cualquier tipo de información de manera consistente en la UI.

classDiagram
    class Envelope {
        +String message
        +Data data
        +List~Suggestion~ uiSuggestions
        +Pagination pagination
        +Metadata metadata
    }

    class Data {
        +String type
        +List~GenericItem~ items
        +Map~String,Any~ summary
    }

    class GenericItem {
        +String id
        +String type
        +String titulo
        +Map~String,Any~ campos
        +List~Action~ actions
    }

    class Suggestion {
        +String id
        +String label
        +String message
        +SuggestionType type
        +Map~String,Any~ context
    }

    class Action {
        +String id
        +String label
        +String endpoint
        +String method
        +Map~String,Any~ params
    }

    class Pagination {
        +Int currentPage
        +Int totalPages
        +Int totalItems
        +Int itemsPerPage
        +String nextPageToken
        +Boolean hasNextPage
        +Boolean hasPreviousPage
    }

    class Metadata {
        +String conversationId
        +String timestamp
        +String model
        +Int tokensUsed
        +Float responseTime
        +String version
    }

    Envelope "1" --> "1" Data : contains
    Envelope "1" --> "*" Suggestion : contains
    Envelope "1" --> "0..1" Pagination : contains
    Envelope "1" --> "1" Metadata : contains
    Data "1" --> "*" GenericItem : contains
    GenericItem "1" --> "*" Action : contains

Arquitectura de Tool Calling Iterativo

Concepto Clave: El Backend Chat usa un sistema de bucle iterativo que permite a OpenAI realizar múltiples llamadas a la API hasta obtener toda la información necesaria.

// OpenAICallApiService.java - Bucle principal
for (int iter = 0; iter < maxIterations; iter++) {
    // 1. Llamar OpenAI con tool "call_api"
    JsonNode response = openai.createResponse(currentMessages, [call_api_tool]);
    
    // 2. Si OpenAI responde con tool_calls:
    if (response.has("tool_calls")) {
        // 3. Ejecutar TODAS las tool_calls solicitadas
        for (toolCall : tool_calls) {
            String result = apiProxyService.call(toolCall);
            toolResults.add(result);
        }
        
        // 4. Agregar resultados como mensajes tipo "tool"
        currentMessages.add(assistantMessage);  // con tool_calls
        currentMessages.addAll(toolResults);     // resultados
        
        // 5. Volver a llamar OpenAI en siguiente iteración
        continue;
    } else {
        // 6. No hay tool_calls → respuesta final
        return response;
    }
}

Características del Sistema:

  • ✅ Máximo 10 iteraciones para evitar bucles infinitos
  • ✅ UN SOLO tool genérico: call_api (puede llamar a cualquier endpoint de la whitelist)
  • ✅ OpenAI puede pedir múltiples tools en una sola respuesta (se procesan todas antes de siguiente iteración)
  • ✅ Whitelist de endpoints: Solo se permiten llamadas a endpoints pre-autorizados
  • ✅ Validación JWT en cada llamada: El mismo JWT del usuario se reenvía a API Workers

Ejemplo de Flujo Iterativo Real:

// Iteración 1:
Usuario: "Muéstrame los alumnos del curso de Matemáticas 1º ESO"
OpenAI: tool_call → GET /cursos?nombre=Matemáticas%201º%20ESO
API Workers: [{ "id": 8, "nombre": "Matemáticas 1º ESO" }]

// Iteración 2:
OpenAI: tool_call → GET /inscripciones?curso_id=8&activas=true&expand=alumno
API Workers: [{ inscripciones con datos de alumnos }]

// Iteración 3:
OpenAI: "El curso Matemáticas 1º ESO tiene 25 alumnos inscritos..." (respuesta final)

Telemetría del Sistema Iterativo:

Métrica Valor Típico Descripción
Iteraciones por request 1-3 (promedio: 2) Mayoría de casos se resuelven en 2 ciclos
Tiempo por iteración 0.5-2 segundos Incluye llamada OpenAI + API Workers
Tiempo total 1-6 segundos Depende de complejidad de la consulta
Casos extremos Hasta 15 segundos Queries complejas con múltiples tool_calls
Tokens consumidos 500-3000 Aumenta con cada iteración

Ventajas del Sistema Iterativo:

  1. Flexibilidad Total: OpenAI decide qué información necesita en cada paso
  2. Optimización de Llamadas: Solo se hacen las consultas necesarias
  3. Resiliencia: Si una tool falla, OpenAI puede intentar otra aproximación
  4. Contexto Acumulativo: Cada iteración enriquece el contexto para mejores respuestas

Desventajas y Mitigaciones:

  • ❌ Mayor latencia: Múltiples round-trips a OpenAI
    • ✅ Mitigación: Usar modelo rápido (gpt-4o-mini) y caché de respuestas frecuentes
  • ❌ Mayor consumo de tokens: Cada iteración suma tokens
    • ✅ Mitigación: Límite de 10 iteraciones, prompts optimizados
  • ❌ Posibles bucles infinitos: OpenAI podría pedir información repetidamente
    • ✅ Mitigación: Límite de iteraciones + logs de detección de patrones

OpenAI GPT-4

  • Responsabilidad: Interpretación de lenguaje natural
  • Decide qué herramientas llamar (function calling)
  • Genera respuestas en lenguaje natural

  • Responsabilidad: Lógica de negocio y acceso a datos

9.4 - Arquitectura del Backend Chat (Spring Boot)

El Backend Chat es el orquestador central del sistema, actuando como intermediario entre la aplicación Android, OpenAI GPT-4 y la API Workers. Esta sección explica en profundidad cómo funciona internamente, qué componentes utiliza y cómo se coordinan.

Por Qué Spring Boot

Spring Boot fue elegido como framework del Backend Chat por las siguientes razones:

  • Anotaciones que Simplifican el Código: Spring Boot utiliza anotaciones como @RestController, @Service y @Autowired que permiten escribir menos código y centrarse en la lógica de negocio. Por ejemplo, no necesitas crear manualmente instancias de servicios, Spring Boot lo hace automáticamente.
  • Inyección de Dependencias Automática: Cuando una clase necesita utilizar otra (por ejemplo, ChatController necesita ChatService), Spring Boot se encarga de "inyectar" automáticamente esa dependencia. Esto hace el código más limpio y fácil de probar.
  • Servidor Web Integrado: Spring Boot incluye un servidor Tomcat embebido, lo que significa que no necesitas instalar ni configurar un servidor web por separado. Simplemente ejecutas la aplicación y ya funciona.
  • Configuración Centralizada: Todas las configuraciones (claves API, URLs, puertos) se guardan en un único archivo application.properties, facilitando el cambio entre entornos (desarrollo, pruebas, producción).
  • Ecosistema Java Maduro: Al usar Java, tenemos acceso a miles de librerías bien documentadas y probadas en producción, especialmente para seguridad (JWT, autenticación) y comunicación HTTP.

Componentes Principales del Backend Chat

El Backend Chat está organizado en capas según el patrón MVC + Services:

9.5 - Arquitectura de la API Workers (Flask + Python)

La API Workers es el componente que gestiona todos los datos del negocio (academias, alumnos, cursos, sesiones, inscripciones, etc.). Está construida con Python y Flask, siguiendo el patrón arquitectónico Domain-Driven Design (DDD).

Por Qué Python y Flask

Python y Flask fueron elegidos para la API Workers por las siguientes razones:

  • Sintaxis Clara y Legible: Python es uno de los lenguajes más fáciles de leer y escribir. El código se parece mucho al lenguaje natural, lo que facilita el mantenimiento y la colaboración. Por ejemplo, crear un endpoint REST es tan simple como decorar una función con @app.route('/alumnos').
  • Flask: Microframework Minimalista: A diferencia de frameworks "grandes" como Django, Flask es muy ligero y solo incluye lo esencial. Tú decides qué componentes añadir (base de datos, autenticación, validación), lo que da mucha flexibilidad para organizar el proyecto a tu manera.
  • Ecosistema Rico para Bases de Datos: Python tiene excelentes librerías para trabajar con bases de datos: SQLAlchemy (ORM que convierte tablas en clases Python), Alembic (migraciones automáticas), PyMySQL (conector para MySQL).
  • Rápido Desarrollo de APIs REST: Con Flask puedes crear un endpoint funcional en menos de 10 líneas de código. Ideal para proyectos donde necesitas muchos endpoints diferentes (en este caso, más de 30 endpoints).
  • Integración con MySQL y AWS: Python se integra perfectamente con MySQL 8.0 (nuestra base de datos) y con los servicios de AWS (Elastic Beanstalk para despliegue, RDS para base de datos gestionada).

Patrón Domain-Driven Design (DDD)

DDD es un patrón de arquitectura de software que organiza el código según el dominio del negocio (en nuestro caso: academias, alumnos, cursos, inscripciones, sesiones). La idea principal es que el código refleje exactamente cómo funciona el negocio real.

¿Qué problema resuelve DDD?

Sin DDD, el código de una API tiende a convertirse en un "gran archivo" donde todo está mezclado: lógica de negocio, acceso a base de datos, validaciones, endpoints HTTP... Esto hace el proyecto difícil de mantener y escalar.

DDD separa el código en capas claramente definidas:

📁 Estructura de Carpetas DDD en la API Workers:

api-workers-profesores/
├── domain/

1. domain/models/ - Conceptos del Negocio Real

Aquí definimos las entidades del dominio: Academia, Alumno, Curso, Inscripcion, Sesion. Estas clases representan exactamente los conceptos que existen en una academia real.

# domain/models/alumno.py
from dataclasses import dataclass
from datetime import date

@dataclass
class Alumno:
    """
    Entidad del dominio: Alumno
    Representa a un estudiante de la academia
    """
    id: int
    nombre: str
    apellidos: str
    dni: str
    fecha_nacimiento: date
    email: str
    telefono: str
    academia_id: int
    
    def edad(self) -> int:
        """Calcula la edad actual del alumno"""
        hoy = date.today()
        return hoy.year - self.fecha_nacimiento.year

2. domain/repositories/ - Interfaces que Abstraen el Acceso a Datos

Los repositorios definen qué operaciones podemos hacer con cada entidad, pero sin especificar cómo (eso se hace en infrastructure/).

# domain/repositories/alumno_repository.py
from abc import ABC, abstractmethod
from typing import List, Optional
from domain.models.alumno import Alumno

class AlumnoRepository(ABC):
    """
    Interfaz que define operaciones sobre Alumnos.
    NO implementa la lógica, solo declara qué operaciones existen.
    """
    
    @abstractmethod
    def buscar_por_dni(self, dni: str) -> Optional[Alumno]:
        """Busca un alumno por su DNI"""
        pass
    
    @abstractmethod
    def listar_por_academia(self, academia_id: int) -> List[Alumno]:
        """Lista todos los alumnos de una academia"""
        pass
    
    @abstractmethod
    def guardar(self, alumno: Alumno) -> Alumno:
        """Guarda un nuevo alumno o actualiza uno existente"""
        pass

Ventaja: Si mañana queremos cambiar MySQL por PostgreSQL, solo modificamos la implementación en infrastructure/, no todo el código.

3. application/services/ - Lógica de Negocio

Los servicios contienen las reglas del negocio. Por ejemplo, al inscribir a un alumno en un curso, hay que:

  1. Verificar que el alumno acepte nuevos cursos (no ha alcanzado máximo)
  2. Verificar que el curso tenga plazas disponibles
  3. Verificar que el alumno no esté ya inscrito
  4. Crear la inscripción en la base de datos
  5. Enviar notificación (opcional)
# application/services/inscripcion_service.py
from domain.repositories.inscripcion_repository import InscripcionRepository
from domain.repositories.curso_repository import CursoRepository

class InscripcionService:
    """
    Servicio que contiene la lógica de negocio para inscripciones
    """
    def __init__(self, 
                 inscripcion_repo: InscripcionRepository,
                 curso_repo: CursoRepository):
        self.inscripcion_repo = inscripcion_repo
        self.curso_repo = curso_repo
    
    def inscribir_alumno(self, alumno_id: int, curso_id: int):
        """
        Inscribe a un alumno en un curso, validando todas las reglas
        """
        # 1. Verificar que el curso existe y tiene plazas
        curso = self.curso_repo.buscar_por_id(curso_id)
        if not curso:
            raise ValueError(f"Curso {curso_id} no encontrado")
        
        if curso.plazas_ocupadas >= curso.capacidad_maxima:
            raise ValueError("Curso sin plazas disponibles")
        
        # 2. Verificar que alumno no esté ya inscrito
        inscripcion_existente = self.inscripcion_repo.buscar_por_alumno_y_curso(
            alumno_id, curso_id
        )
        if inscripcion_existente:
            raise ValueError("Alumno ya está inscrito en este curso")
        
        # 3. Crear inscripción
        return self.inscripcion_repo.crear_inscripcion(alumno_id, curso_id)

Ventaja: Toda la lógica compleja está en un solo lugar, no dispersa por múltiples archivos.

4. infrastructure/ - Implementación Técnica con SQLAlchemy y Flask

Aquí es donde finalmente conectamos con MySQL usando SQLAlchemy (un ORM que convierte tablas en clases Python).

# infrastructure/alumno_repository_impl.py
from domain.repositories.alumno_repository import AlumnoRepository
from domain.models.alumno import Alumno
from sqlalchemy.orm import Session

class AlumnoRepositoryImpl(AlumnoRepository):
    """
    Implementación real del repositorio usando SQLAlchemy + MySQL
    """
    def __init__(self, db_session: Session):
        self.db = db_session
    
    def buscar_por_dni(self, dni: str) -> Optional[Alumno]:
        """
        Ejecuta una consulta SQL para buscar alumno por DNI
        """
        # SQLAlchemy convierte esto en: SELECT * FROM alumnos WHERE dni = :dni
        resultado = self.db.query(AlumnoModel).filter(AlumnoModel.dni == dni).first()
        
        if resultado:
            # Convertir de AlumnoModel (SQLAlchemy) a Alumno (dominio)
            return Alumno(
                id=resultado.id,
                nombre=resultado.nombre,
                apellidos=resultado.apellidos,
                dni=resultado.dni,
                fecha_nacimiento=resultado.fecha_nacimiento,
                email=resultado.email,
                telefono=resultado.telefono,
                academia_id=resultado.academia_id
            )
        return None

Ventaja: SQLAlchemy genera las queries SQL automáticamente. No escribimos SQL a mano, reduciendo errores.

# infrastructure/task_routes.py
from flask import Blueprint, request, jsonify
from application.services.inscripcion_service import InscripcionService

# Crear un "Blueprint" (grupo de rutas relacionadas)
bp = Blueprint('inscripciones', __name__)

@bp.route('/inscripciones', methods=['POST'])
def inscribir_alumno():
    """
    POST /inscripciones
    Body: {"alumno_id": 12, "curso_id": 5}
    """
    data = request.get_json()
    
    try:
        # Delegar lógica al servicio
        inscripcion_service = InscripcionService(inscripcion_repo, curso_repo)
        resultado = inscripcion_service.inscribir_alumno(
            alumno_id=data['alumno_id'],
            curso_id=data['curso_id']
        )
        
        return jsonify({
            "ok": True,
            "data": {
                "inscripcion_id": resultado.id,
                "mensaje": "Alumno inscrito exitosamente"
            }
        }), 201
    
    except ValueError as e:
        return jsonify({
            "ok": False,
            "error": str(e)
        }), 400

A. Glosario de Términos

Envelope: Estructura de datos estándar que envuelve todas las respuestas del chat.

GenericItem: Objeto polimórfico que representa cualquier entidad (alumno, curso, sesión, etc.).

Tool Calling: Mecanismo de OpenAI para que el LLM solicite ejecutar funciones externas.

served-openapi.json: Especificación de la API en formato OpenAPI que se envía a GPT-4.

SessionStore: Almacén local (DataStore) de tokens y datos del usuario.

Context Map: Mapa de datos que viaja con cada mensaje para mantener estado conversacional.

Mock: Implementación simulada de un repositorio para desarrollo sin backend.

JWT: JSON Web Token, estándar para autenticación basada en tokens. En nuestro sistema viaja sin modificarse desde Android hasta MySQL.

Claims: Datos incluidos en el JWT (usuarioId, academiaId, role, email, exp, iat).
