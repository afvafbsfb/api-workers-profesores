2. OBJETIVO

Desarrollar una plataforma SaaS completa para gestión de academias que utiliza inteligencia artificial conversacional (OpenAI GPT-4) como ÚNICA interfaz de usuario, sustituyendo pantallas y formularios tradicionales por una experiencia de chat conversacional que permite realizar todas las operaciones administrativas mediante lenguaje natural.

Objetivo Secundario: Diseñar una arquitectura modular y reutilizable que permita adaptar el Backend Chat conversacional a otros sectores de negocio (autoescuelas, gimnasios, etc.) mediante cambios mínimos en la whitelist de funciones y los prompts de sistema, maximizando el retorno de inversión del desarrollo inicial.

3. DESCRIPCIÓN

3.1. Motivación Personal

La motivación para este proyecto surge de mi convicción de que la Inteligencia Artificial va a transformar radicalmente el desarrollo de software y las aplicaciones para clientes finales.

Observando el panorama actual, veo que muchos profesionales autónomos y pequeñas empresas están desbordados de trabajo administrativo, sin tiempo ni recursos para adoptar soluciones digitales complejas. Esa ayuda les va a llegar en forma de trabajadores virtuales que les asistan de manera sencilla, usando lenguaje humano natural, para resolver las necesidades específicas de su negocio.

Las pequeñas academias y negocios de formación representan perfectamente este escenario: gestión compleja (alumnos, horarios, pagos, asistencias) pero recursos limitados y personal sin formación técnica. La pregunta clave que motiva este proyecto es:

"¿Y si pudiéramos gestionar todo esto hablando con la aplicación como si fuera un asistente humano?"

Esta idea evolucionó hacia un concepto ambicioso: eliminar completamente las pantallas tradicionales de formularios y reemplazarlas por una interfaz conversacional inteligente capaz de entender lenguaje natural y ejecutar operaciones complejas de forma automática.

El reto técnico era formidable: hacer que una IA entienda contexto empresarial, resuelva operaciones CRUD mediante conversaciones, mantenga seguridad a nivel empresarial y ofrezca una experiencia de usuario fluida. Este proyecto representa un caso práctico de cómo los trabajadores virtuales con IA pueden revolucionar la digitalización de pequeños negocios.

Capa Tecnología Responsabilidad

3.3.2. Patrón Arquitectónico Clave: Token Delegation

Una de las decisiones arquitectónicas más importantes del proyecto es el patrón de Token Delegation:

  • El mismo JWT del usuario viaja sin modificarse desde Android hasta MySQL
  • Backend Chat NO genera un nuevo token, simplemente reenvía el del usuario
  • Esto garantiza trazabilidad completa: cada acción en cada capa está asociada al mismo usuarioId
  • Implementa multi-tenancy implícito: el academiaId del JWT filtra automáticamente los datos

Ver diagrama de flujo completo en sección 8.2 y Anexo H: Diagramas de Secuencia.

3.4. Dificultades Técnicas

El desarrollo del proyecto presentó desafíos técnicos significativos, propios de trabajar con tecnologías emergentes (IA generativa) y arquitecturas distribuidas:

3.4.1. Token Delegation Architecture

Problema

¿Cómo mantener la identidad del usuario a través de 4 capas heterogéneas (Kotlin → Java → Python → MySQL) sin comprometer la seguridad?

Solución Implementada

Patrón de token delegation con secret compartido entre Backend Chat y API Workers. El JWT se valida en ambas capas con la misma clave, garantizando que:

  • Android genera el JWT tras login exitoso
  • Backend Chat lo valida (claims: usuarioId, academiaId, role)
  • Backend Chat lo reenvía SIN modificar a API Workers
  • API Workers lo valida de nuevo
  • MySQL registra usuarioId en campos de auditoría

Ver implementación en Anexo I: Código Fuente Destacado - ApiProxyService.java

3.4.2. Latencia LLM (8-13 segundos)

Problema Identificado Durante Desarrollo

Al trabajar con OpenAI GPT-4, se descubrió que las operaciones tardan 8-13 segundos, muy por encima del objetivo de <3s. Esto es un hallazgo propio del carácter innovador del proyecto: trabajar con modelos de IA generativa presenta desafíos de performance no documentados en el ciclo formativo.

Diagnóstico Realizado

Mediante análisis profundo del sistema de prompts, se identificó la causa raíz:

  • Whitelist completa (2,557 líneas de OpenAPI) enviada como texto en cada turno
  • Consumo de ~7,000 tokens innecesarios (44% del total)
  • GPT-4 debe procesar especificación completa aunque solo use 1-2 endpoints

Plan de Solución Propuesto (8 Semanas)

Se ha diseñado un plan de reingeniería en 3 fases con 5 técnicas de optimización:

  1. Function Calling Schema: Usar parámetro nativo de OpenAI → -88% tokens
  2. Semantic Cache con Redis: Cache vectorial para queries repetidas → 40-60% hit rate
  3. Streaming SSE: Respuesta progresiva → TTFB <300ms (vs 8s)
  4. Two-Stage Architecture: gpt-4o-mini para queries simples → -94% latencia
  5. Prompt Compression: Formato compacto whitelist → -90% tokens

Impacto proyectado: -81% latencia, -73% costo

Importante: Este problema NO es una limitación del proyecto, sino un descubrimiento técnico valioso que demuestra capacidad de análisis, diagnóstico y propuesta de soluciones en tecnologías emergentes. Ver documentación completa en Anexo E: Ingeniería de Prompts y Optimización LLM.

3.4.3. Foreign Key Resolution Automática

Problema

Para crear un usuario, la API requiere rol_id. Pero el usuario conversacional dice: "Crear profesor Juan Pérez" (sin conocer IDs).

Solución: Multi-Turno Inteligente

Sistema automático implementado en el prompt:

  1. GPT-4 detecta que necesita rol_id
  2. Primer tool call: GET /roles
  3. Extrae ID del rol "Profesor_academia"
  4. Segundo tool call: POST /usuarios con rol_id correcto
  5. Respuesta al usuario: "Usuario creado correctamente"

3.4.4. Multi-Tenancy Implícito

Problema

Garantizar que un profesor de la Academia A NO pueda ver datos de la Academia B, sin programar filtros explícitos en cada endpoint.

Solución: Filtrado Automático por academiaId

Para roles admin_academia y profesor_academia, el academiaId del JWT se inyecta automáticamente en todas las queries SQL:

SELECT * FROM Curso WHERE academia_id = {academiaId_from_JWT}

El desarrollador NO necesita recordar añadir este filtro. Es gestionado por decoradores en Python (API Workers).

Caso especial - admin_plataforma: Este rol NO tiene academia_id en su JWT (gestiona múltiples academias). Puede especificar opcionalmente academia_id en los parámetros de la query. Si no lo especifica, puede consultar datos de todas las academias.

Implementación real: src/shared/application/permissions.py (función can_query_* con enforced_filters, líneas 145-178 muestran cómo admin_plataforma puede filtrar opcionalmente por academia_id mientras que otros roles lo tienen forzado), src/shared/auth_helpers.py (decorador require_role_kind), src/autenticacion/infrastructure/jwt_provider.py (inclusión de academia_id en JWT solo para roles de academia).

4.3. Justificación de Decisiones Técnicas

4.3.1. ¿Por qué OpenAI GPT-4?

  • Function Calling Nativo: GPT-4o soporta tool calling de forma nativa. El sistema implementa un límite de hasta 10 llamadas iterativas a la API Workers (consultar alumnos, crear sesiones, pasar lista, etc.) para evitar bucles infinitos y controlar costes
  • API REST estándar: Integración directa desde Spring Boot mediante cliente HTTP (biblioteca OpenAI Java SDK)
  • Modelo GPT-4o: Versión optimizada con mejor balance velocidad/calidad para aplicaciones conversacionales en producción
  • Comprensión en español: Interpreta correctamente consultas en lenguaje natural coloquial ("¿cuántos alumnos vinieron hoy?")

Arquitectura Tool Calling: Ver Documentación Técnica - Sección 10.1: Backend Chat para explicación detallada del sistema de prompts dinámicos y bucle iterativo de tool calling (clase `PromptOpenAi.java`, 699 líneas).

4.3.2. ¿Por qué Jetpack Compose y no XML tradicional?

  • UI Declarativa: Código Kotlin que define "qué mostrar" en lugar de "cómo construirlo" mediante XML. Los componentes se recomponen automáticamente cuando cambia el estado
  • Tecnología actual: Jetpack Compose 1.5.4 es el toolkit moderno de Android desde 2021, recomendado oficialmente por Google para nuevos proyectos
  • Chat conversacional: Facilita renderizado dinámico de mensajes, tablas (`LazyColumn`) y formularios sin gestionar layouts XML estáticos
  • MVVM + StateFlow: Patrón arquitectónico con `ViewModel` reactivo que emite estados inmutables mediante `StateFlow`, observados desde Composables

Documentación arquitectura Android: Ver AcademiaAPP/documentacion/ARQUITECTURA_ACADEMIAAPP_ANDROID.html (patrón MVVM con Compose + StateFlow) y UX_ACADEMIAAPP_ANDROID.html (diseño interfaz conversacional con tablas/listas dinámicas)

4.3.3. ¿Por qué Python para API Workers y no Java?

  • Flask: Framework web minimalista que permite crear APIs REST de forma rápida y flexible
  • SQLAlchemy 2.0: ORM moderno que mapea tablas MySQL a clases Python, simplificando operaciones CRUD
  • Marshmallow 3.20: Biblioteca de validación y serialización que convierte objetos Python a JSON (y viceversa) automáticamente
  • Desarrollo rápido: Python requiere menos líneas de código que Java para implementar la misma funcionalidad
  • Patrón Domain-Driven Design: Arquitectura organizada por dominios de negocio (alumnos, cursos, sesiones, pagos)

Arquitectura detallada: Ver Documentación Técnica Completa - Sección 10.2: Arquitectura API Workers para explicación completa del patrón DDD, estructura de carpetas y flujo de datos.

4.3.4. ¿Por qué Spring Boot para el Backend Chat?

  • Spring Boot 3.5.5: Framework empresarial maduro con ecosistema completo para desarrollo de microservicios
  • Java 21: Versión LTS moderna con mejoras de rendimiento, records, pattern matching y Virtual Threads
  • OpenAI Java SDK: Cliente oficial de OpenAI que simplifica la integración con GPT-4o y function calling
  • Ecosistema robusto: Spring Security para JWT, Spring Web para REST, Jackson para JSON, Lombok para reducir boilerplate
  • Tipado estático: Detección de errores en tiempo de compilación, refactoring seguro y mejor mantenibilidad
  • Rendimiento: JVM optimizada para aplicaciones de alta concurrencia y baja latencia
  • Separación de responsabilidades: Backend Chat como orquestador inteligente (IA + lógica de negocio compleja), API Workers como capa de datos (CRUD simple)

Arquitectura detallada: Ver Documentación Técnica Completa - Sección 10.1: Arquitectura Backend Chat para explicación completa de la estructura de paquetes, PromptOpenAi.java (699 líneas) y sistema de delegation.

8. DEMOSTRACIÓN DEL SISTEMA

8.1. Decisiones de Diseño Clave

8.1.1. ¿Por qué Chat como Interfaz Única?

Problema tradicional: Interfaces CRUD requieren conocimiento técnico y curva de aprendizaje

Solución propuesta: Interfaz conversacional tipo WhatsApp

Beneficios:

  • ✅ Cero curva de aprendizaje: Todo el mundo sabe usar WhatsApp
  • ✅ Accesible para no técnicos: Profesores sin conocimientos informáticos
  • ✅ Reducción de errores: IA valida intents antes de ejecutar
  • ✅ Multioperación: "Crear 3 cursos" en una sola frase
  • ✅ Asistencia contextual: IA sugiere próximos pasos

8.1.2. ¿Por qué Envelope Universal?

En lugar de crear 20 DTOs diferentes (uno por cada entidad: Curso, Usuario, Sesión, etc.), se implementó un contenedor polimórfico:

{ "message": { "text": "Encontré 3 cursos", "ui_suggestions": [ { "type": "Paginacion", "label": "Ver más cursos", ... }, { "type": "Generica", "label": "Crear nuevo curso", ... } ] }, "data": { "type": "curso", "items": [ { "id": "1", "title": "Acuarela Básica", "subtitle": "Prof. Juan López", "extraData": { "precio": 45, "plazas": 12, ... } }, ... ] }, "pagination": { "hasMore": true, "nextToken": "..." } }

Ventaja: Android puede procesar cualquier entidad con el mismo código UI.
