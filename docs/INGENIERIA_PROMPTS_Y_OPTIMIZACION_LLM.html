1. Resumen Ejecutivo

El sistema implementa un asistente conversacional inteligente basado en OpenAI GPT-4 que permite realizar operaciones CRUD mediante lenguaje natural en español.

Indicadores de Madurez Técnica

  • ✓ 90% de cumplimiento de best practices de OpenAI
  • ✓ Arquitectura multi-turno con gestión de estado
  • ✓ Prompts estructurados con ejemplos few-shot
  • ⚠ Optimización de latencia: Principal área de mejora identificada

Características Clave

  • Interfaz conversacional en castellano de España
  • Control de acceso basado en roles (Admin_plataforma, Admin_academia, Profesor_academia)
  • Resolución automática de Foreign Keys mediante llamadas multi-turno
  • Validación y confirmación de operaciones de mutación (PUT/DELETE)
  • Generación dinámica de sugerencias UI tipadas por contexto

2. Arquitectura de Prompts

Componente Principal: PromptOpenAi.java

  • Ubicación: src/main/java/com/workers/profesores/chat/prompt/PromptOpenAi.java
  • Líneas de código: 699
  • Responsabilidad: Construcción dinámica de system prompts según turno de conversación

Tipos de Prompts

Tipo Método Tokens Uso
System Prompt Completo buildSystemPrompt() 15,000-20,000 Primer turno de conversación
System Prompt Compacto buildSecondTurnSystemPrompt() 3,000-5,000 Segundo turno (sin whitelist)
Instrucción 2º Turno buildSecondTurnInstruction() 2,000-3,000 Redacción respuesta final
Instrucción Reformateo buildReformatInstruction() 500-1,000 Convertir texto a JSON

Estructura del System Prompt Completo

  1. Definición de Rol: Asistente (secretaria) para plataforma de academias
  2. Whitelist de Endpoints: Tabla renderizada desde OpenAPI (2,557 líneas)
  3. Contexto Usuario: Roles, academia_id, perfil JSON completo
  4. Warnings de Confusión: ~100 líneas advirtiendo NO confundir usuario logueado con usuarios a crear
  5. Resolución de FKs: GET obligatorio antes de POST/PUT (ejemplo: GET /roles → POST /usuarios)
  6. Contrato JSON: text (obligatorio), ui_suggestions (2-3 tipadas), summary_fields
  7. UI Suggestions: Paginacion, Registro (Alta/Baja/Modificacion), Generica
  8. Herramientas: call_api (una llamada), call_api_batch (varias)
  9. Reglas de Mutación: Confirmación obligatoria para PUT/DELETE
  10. Manejo de Errores: 400/403/404/409/500 con interpretación contextual

5. Problema Actual Identificado

🔴 Cuello de Botella: Latencia Inaceptable

Síntomas Observados

  • Operaciones simples (GET): 5-8 segundos
  • Operaciones con FK (GET+POST): 10-15 segundos
  • Operaciones batch: 15-25 segundos

Causa Raíz

Envío de whitelist completa (2,557 líneas de OpenAPI) como texto en cada turno

Desglose de Tokens

Componente Tokens % del Total Necesario Turno 2+
Whitelist completa 7,000 28% ✗ No

Contexto usuario 3,000 12% ✓ Sí

Tokens innecesarios por request: ~11,000 (44% del total)

Impacto en UX

  • Tasa de abandono (timeout): ~15%
  • Satisfacción usuario: 6.5/10
  • Feedback: "El chat es muy inteligente pero tarda demasiado"

6. Plan de Optimización

✅ Estrategia de Mejora: 5 Soluciones Técnicas

Solución 1: Function Calling Schema CRÍTICA

Problema: Envío de whitelist completa como texto
Solución: Usar parámetro functions nativo de OpenAI
Impacto:

  • Reducción tokens input: -88% (25K → 3K)
  • Reducción latencia: -75% (8s → 2s)
  • Reducción costo: -70% ($0.03 → $0.01)

Solución 2: Semantic Cache con Redis

Problema: Queries repetidas llaman a OpenAI siempre
Solución: Cache vectorial con embeddings (similarity ≥0.95)
Impacto:

  • Cache hit rate: 40-60%
  • Respuesta en cache hit: <100ms
  • Ahorro de costos: ~50%

Solución 3: Streaming Responses (SSE)

Problema: Usuario espera 8s sin feedback
Solución: Server-Sent Events con respuesta progresiva
Impacto:

  • TTFB (Time To First Byte): 300-500ms (vs 8s)
  • Percepción de rapidez: 10x mejor

Solución 4: Two-Stage Architecture

Problema: Queries simples usan GPT-4 completo
Solución: Stage 1 con gpt-4o-mini (intent detection) + Stage 2 GPT-4 (casos complejos)
Impacto:

  • Queries simples: 500ms (vs 8s) = -94%
  • Costo reducido: -70%
  • ~60% de queries son simples

Solución 5: Prompt Compression

Problema: Whitelist verbosa con info redundante
Solución: Formato compacto (1 línea por endpoint)
Impacto:

  • Compresión: ~90% en whitelist (300 tokens → 30 tokens por endpoint)
  • Tokens whitelist: 7,000 → 700
